# LibreChat + Model Council design for the second brain

Written 2026-08-24, against the nas-ops state as of TASKS.md/CLAUDE.md's 2026-08-20/21 entries. Intended as a design document for Claude Code to build against, not as something Cowork should implement directly — per your own working-principle decision (nas-ops CLAUDE.md, deferred decision #5), hands-on NAS execution stays with Claude Code over SSH; Cowork's role here is planning.

## What "model council" means here

The pattern is Andrej Karpathy's [llm-council](https://github.com/karpathy/llm-council): a query goes to several models at once, each answers independently, each then reviews the others' answers with identities anonymized and ranks them, and a designated "chairman" model reads all the answers and rankings and writes one synthesized final answer. Karpathy's reference implementation runs as a small FastAPI + React app, calls models through OpenRouter, and lists `openai/gpt-5.1`, `google/gemini-3-pro-preview`, `anthropic/claude-sonnet-4.5`, and `x-ai/grok-4` as example council members in `backend/config.py` — worth treating as illustrative rather than fixed, since OpenRouter model slugs shift and should be checked at build time.

Worth being direct about one thing up front: LibreChat does not have this built in. There's an open, unresolved feature request for even basic side-by-side multi-model comparison ([danny-avila/LibreChat#3659](https://github.com/danny-avila/LibreChat/issues/3659)) — parallel fan-out, anonymized peer review, and chairman synthesis are Karpathy's own orchestration logic, not a LibreChat feature you can toggle on. So "aligning LibreChat with the model council" means deciding how much of that orchestration to build versus approximate, not finding a setting for it.

Perplexity shipped a consumer version of the same underlying pattern, [Model Council](https://www.perplexity.ai/hub/blog/introducing-model-council): pick 2–8 models (now including open-weight options alongside OpenAI/Anthropic/Google — GLM and Kimi are both on their list, the same two Chinese models scoped above, which is a useful external signal that they're being taken seriously as council-grade models industry-wide), run each as a full parallel subagent, and have a user-chosen "chair" model synthesize one report that explicitly shows where the models agree and diverge. It's the same lineage as Karpathy's design but has quietly dropped the anonymized peer-ranking stage in favor of going straight from independent answers to chair synthesis — worth knowing since it means "Model Council" isn't a single fixed spec across the industry; anyone building or evaluating one of these should check whether peer review is actually present or just a synthesizer reading raw answers. It's also not a substitute for what's designed here: it's a closed, hosted feature gated to Perplexity Max subscribers, web-grounded rather than connected to any private knowledge base, and there's no confirmation it's reachable via API — it can't call `second-brain-mcp` or attach to your own data, which is the entire point of this design.

## What's already in place

Per TASKS.md and CLAUDE.md, the foundation is further along than a from-scratch design would assume. `second-brain-mcp` is deployed and already wired into LibreChat, exposing `query_second_brain` (merged semantic search over the `second_brain` and `zotero_library` Qdrant collections, same embedding model so scores compare directly, Obsidian-wikilink and `zotero://` citations on every hit) and `map_outline_to_second_brain` (Zotero-collection-scoped search). LibreChat itself is deployed at `/volume1/docker/librechat/`, reachable over Tailscale, with Anthropic as the only model provider currently configured — real key reused from the ingest-digest pipeline, MongoDB moved to Atlas M0 because the NAS's Celeron J3355 has no AVX support. It is explicitly not yet the daily driver; that migration (memory, context-seeding, model comparison) is still deferred architecture decision #3 in your own CLAUDE.md, not started. Whatever "Code" is doing right now to `query.py`/the MCP wrapper slots into this design the same way regardless of what changes — the council designs below only depend on `query_second_brain` existing and returning cited, scored results, which is already true.

## Is LibreChat the right foundation? Two alternatives worth checking before building on it further

Worth raising before investing more in the LibreChat-specific design below: two other self-hostable, actively maintained tools each solve one half of this problem better than LibreChat does, though neither solves both halves the way LibreChat currently does. This is effectively the same open question as deferred architecture decision #3 in your CLAUDE.md ("LibreChat as default Claude replacement") — worth treating this as a chance to widen that decision to "LibreChat vs. alternatives," not just "when do we make LibreChat the daily driver," given it's still unstarted anyway.

[Big-AGI](https://github.com/enricoros/big-AGI)'s Beam feature is a much closer match to "model council" than anything LibreChat has — but it cannot currently reach `second-brain-mcp`, and this is confirmed, not just unverified. Beam itself is real and native: one prompt fanned out across N models in parallel, merged via three built-in synthesis algorithms (Fuse, Guide, Score) plus custom merge prompts, with a "Council" mode in development, and native support for Claude, GPT, Gemini, DeepSeek, Kimi, and GLM — literally the roster scoped above. But I checked the actual GitHub repo rather than resting on the earlier "no confirmed evidence" caveat, and the gap is real: [Issue #892, "Support MCP,"](https://github.com/enricoros/big-AGI/issues/892) was opened November 28, 2025, is still open, and has zero branches or pull requests attached — nobody has started building it. More tellingly, the prerequisite for MCP support — any general, vendor-agnostic way for a user to register a custom external tool at all — is also unbuilt: [Issue #574, "Roadmap: OpenAI function calling,"](https://github.com/enricoros/big-AGI/issues/574) is older, also open, also with no linked work. The customizations doc confirms this directly: the only things a self-hosted Big-AGI instance can be configured with are provider API keys, deployment variables, and basic auth — nothing about tools. What Big-AGI does ship is provider-native tool use (DeepSeek's own tool-use mode, OpenAI's code interpreter, Anthropic Skills) — built-in capabilities each model provider supplies, not a general extensibility point external servers like `second-brain-mcp` could plug into. Net: Beam is worth trialing purely as a synthesis engine for general-knowledge or manually-pasted-context questions, but it is not a near-term home for a vault-grounded council — the MCP gap isn't a documentation blind spot, it's a real, stalled, unstaffed feature request.

[Onyx](https://github.com/onyx-dot-app/onyx) is a much closer match to the second-brain/citation half — and it's already a named influence on this project's own design, since `query.py`'s citation discipline was explicitly built in the "Onyx-style" per your own TASKS.md entry. Digging further past the surface comparison confirms the good half of this and surfaces one real new problem.

The good half: Onyx's licensing and MCP client are both genuinely solid, not just claimed. It's MIT-licensed — Community Edition covers the full Chat/RAG/Agents/Actions feature set for free, with a separate paid Enterprise Edition adding only SSO, RBAC, audit logging, and whitelabeling, none of which gate anything relevant here. There's also a dedicated `onyx-foss` mirror kept "100% MIT-licensed and automatically synced" with the main repo, for anyone who wants a guarantee against license drift — worth using that mirror specifically if you go this route, given this project's own preference for verifying rather than trusting a vendor's framing. The MCP client is real: Admin Panel → MCP Actions connects to a self-hosted server over HTTP and lets you curate which tools get exposed to Agents, which would let it reach `second-brain-mcp` directly, transport permitting (Onyx's client is HTTP-only, not stdio — still worth checking against how `second-brain-mcp` is actually exposed).

The new problem is resource sizing, and it's a real constraint, not a minor caveat. Onyx ships two deployment modes, and they're not a small/large version of the same thing — they're functionally different products. Lite mode is genuinely light (2 vCPU / 2GB RAM minimum, under 1GB baseline), but per Onyx's own configuration docs it disables all data source connectors and document indexing/RAG search entirely — it's a bare chat-plus-uploaded-files interface, not a knowledge-base tool, and the docs' wording suggests document indexing runs through Vespa specifically in this mode. Standard mode — the one that actually does RAG over indexed sources, which is the entire reason to consider Onyx — needs 4 vCPU minimum (8+ preferred) and 10GB RAM minimum, 16GB+ preferred, per Onyx's own resourcing docs (which describe Standard's index as OpenSearch-backed, a detail that doesn't fully square with the Vespa mention in the configuration docs — worth resolving which is current before relying on either). Either way, Standard mode's real minimum is roughly double your NAS's entire RAM headroom (~7GB, already shared across everything else running), so it isn't a NAS candidate at all — it would need its own VPS sizing, and a meaningfully larger VPS than the CHF 20–40/month estimate your CLAUDE.md already has budgeted for the whole second-brain stack, not just one chat frontend. One thing I couldn't confirm either way: whether MCP Actions specifically require Standard mode's full indexing stack to be running, or whether Lite mode can still expose external MCP tools like `second-brain-mcp` while just not using Onyx's own connectors/indexing — if the latter, Lite mode might actually be viable here after all, purely as an MCP-client chat shell rather than a second indexing layer duplicating what Qdrant already does. Worth a direct test rather than assuming either way.

Onyx has nothing like Beam, either; a council on top of it would still mean building the fan-out/synthesis logic yourself, same as the LibreChat plan.

Net effect: neither alternative is a clean win over LibreChat, and both gaps are now concrete rather than open questions. Big-AGI's MCP gap is confirmed stalled — a 9-month-old feature request with zero linked work — so it's a synthesis-only tool for now. Onyx's MCP client and licensing are genuinely solid, but Standard mode's resource footprint (10GB+ RAM, 4+ vCPU) rules out the NAS outright and is heavier than the whole stack's current VPS budget, unless Lite mode turns out to support MCP Actions without the indexing stack — an open, checkable question, not a confirmed workaround. The pragmatic case for staying on LibreChat for now holds up better after this digging, not worse: it's already deployed, already has `second-brain-mcp` wired in and proven working (TASKS.md, 2026-08-15), runs fine on the NAS today, and gets you a working manual council with zero new infrastructure per Phase 1 below. The rest of this document assumes LibreChat accordingly. Onyx is still worth a real trial, but the honest framing has changed: not "a quick concrete check," but "worth resolving the Lite-mode-plus-MCP question first, since if that doesn't work, Onyx-as-daily-driver is really a VPS-sizing decision, not a swap-in."

## Phase 1 — council inside LibreChat's existing Agents, no new infrastructure

This gets you a working (if manual) council today, using only what LibreChat already does natively, and costs nothing to build beyond config.

Add one new custom endpoint to `librechat.yaml` for the non-Anthropic council members, routed through OpenRouter, so you're not managing five separate provider keys:

```yaml
endpoints:
  custom:
    - name: 'Council (OpenRouter)'
      apiKey: '${OPENROUTER_API_KEY}'
      baseURL: 'https://openrouter.ai/api/v1'
      models:
        default:
          - 'google/gemini-3-pro-preview'
          - 'deepseek/deepseek-v4-pro'
          - 'moonshotai/kimi-k3'
          - 'z-ai/glm-5.2'
        fetch: false

```

Deliberately leave Claude on the existing native Anthropic endpoint rather than also routing it through OpenRouter — you already made this exact call once, when you rejected Open WebUI's OpenAI-compatibility-only routing specifically because it loses prompt caching (TASKS.md, LibreChat deployment entry). Same reasoning applies to a council member. See "Scoping the initial roster" below for why this list looks different from a default Western-frontier lineup, and for the Chinese open-weight models it adds.

In LibreChat's Agent Builder, create five "council member" agents — one on Claude Sonnet 4.5 (native endpoint), one each on Gemini 3 Pro, DeepSeek V4 Pro, Kimi K3, and GLM-5.2 (the new OpenRouter endpoint) — and attach the `second-brain-mcp` tools to all five, so every member grounds its answer in your own vault and Zotero library rather than answering from general knowledge alone. Add a sixth agent, "Chairman," on whichever model you trust most for synthesis (Claude Sonnet 4.5 is a reasonable default given it's already your daily model, though GLM-5.2's explicit agent-orchestration design is worth A/B testing for this specific role), also with `second-brain-mcp` attached, and give it a system prompt that asks it to read pasted-in answers from the other five, note where they agree and disagree, and produce one synthesized answer that preserves each underlying citation rather than smoothing them away.

The gap versus real Karpathy-style orchestration is the fan-out and hand-off: you're asking the same question in five conversations and pasting the five answers into the Chairman's conversation yourself, rather than getting one-click parallel dispatch and automatic anonymized peer ranking. That's real friction, but it's also a reasonable way to find out whether a council actually earns its keep on your research questions before you build automation for it.

## Scoping the initial roster, including Chinese open-weight models

The obvious way to add Chinese open-weight models is to bolt them onto the four-Western-model lineup from Karpathy's own example config, making a council of seven or eight. That's worth resisting: the point of a council, per the weaknesses discussion below, is genuine diversity of training lineage and alignment approach, not headcount, and GPT-5.1, Gemini 3 Pro, and Grok 4 likely share more correlated blind spots with each other and with Claude — similar English-dominant web-scale pretraining data, broadly similar RLHF methodology, similar-shaped safety tuning — than any of them do with a Chinese lab. Trading two of those three Western seats for two Chinese open-weight seats does more for the council's actual epistemic diversity than just adding more members on top. Everything below was checked live against OpenRouter's model catalog and each lab's own release material on 2026-08-24, not recalled from training data, since this space moves in weeks, not months, and the exact slugs, licenses, and even the current flagship version numbers should be re-checked at build time regardless.

The five-seat roster proposed above is: Claude Sonnet 4.5 (native, kept for caching and as your daily-driver anchor); Gemini 3 Pro (`google/gemini-3-pro-preview`) as the sole additional Western model, kept mainly for its very large context handling, which matters given how long your wiki pages and Zotero chunks can run; DeepSeek V4 Pro (`deepseek/deepseek-v4-pro`) — MIT-licensed, a 1.6T-total/49B-active MoE with a 1M-token context and three reasoning modes (including a "Think Max" setting), currently the single most-used model on OpenRouter by tokens processed, which is a real signal of production reliability at scale, not just benchmark performance; Kimi K3 (`moonshotai/kimi-k3`) from Moonshot AI — open weights (1.4TB of files on Hugging Face) under a custom commercial license, a 2.8T-total/104B-active MoE with 1M-token context and native multimodal support (potentially useful later for reasoning over Boox page images or Zotero PDF figures directly, rather than only OCR'd text), and reported as narrowly leading several current benchmarks; and GLM-5.2 (`z-ai/glm-5.2`) from Zhipu/Z.ai — MIT-licensed, 753B-total/40B-active MoE with 1M-token context, explicitly built and marketed as "agent-oriented" with strong multi-turn tool orchestration, which makes it a particularly good fit for a role that needs to call `query_second_brain` well, whether as a member or as chairman.

Two more Chinese open-weight models are worth configuring even though they're not proposed as initial council seats. MiniMax M2 (`minimax/minimax-m2`, MIT, 230B-total/10B-active) is deliberately small — cheap and fast enough to be a sensible default model for plain `query_second_brain` lookups outside full council mode, and also a candidate for doing the peer-ranking pass inside a future `council-mcp` (that step needs judgment more than raw generative scale). It's also the one model in this whole list small enough to realistically consider self-hosting later if the VPS ever gets real GPU capacity — everything else here is a paid-API-only proposition regardless of the weights being open, given the NAS's and any near-term VPS's likely hardware. Check whether MiniMax's newer M2.5 or M2.7 (both appear in OpenRouter's catalog as `minimax/minimax-m2.5` / `minimax/minimax-m2.7`) has superseded M2 as the better default by the time this gets built. Qwen3.8 from Alibaba comes in two very different forms worth knowing apart: the 27B version (`qwen/qwen3.8-27b`) ships under plain Apache 2.0 with no commercial strings attached at all, making it the cleanest possible self-hosting candidate alongside MiniMax M2; the 2.4T flagship (`qwen/qwen3.8-max`) ships under a custom license that only imposes real obligations — a required attribution notice, or a separate commercial license — on products clearing 100M monthly active users, $20M/month revenue, or $50M/year revenue from a hosted AI service, all of which are irrelevant at personal-research scale but worth knowing if any of this vault work ever gets shared or productized.

Licensing is genuinely permissive for personal use across the board here: DeepSeek V4, GLM-5.2, MiniMax M2, and Qwen3.8-27B are plain MIT or Apache 2.0; Kimi K3 and Qwen3.8-Max carry custom commercial licenses whose restrictions only bite at a commercial scale far beyond a personal second brain. The one question worth deciding deliberately rather than defaulting past is jurisdictional: routing a query through a Chinese lab's model — even via OpenRouter as a US-based intermediary rather than a direct account relationship — means your prompt (which, in a grounded council query, includes retrieved passages from your Zotero library and vault) is processed on that lab's inference infrastructure, subject to Chinese data-handling rules. You've already treated this kind of question deliberately elsewhere in the project — it's the same reasoning behind the Swiss-jurisdiction VPS candidate, and behind flagging Boox notes as more privacy-sensitive than curated Zotero or public social content in the karpathy-llm-wiki-implications.md doc. Worth deciding explicitly whether that's fine for citation-grade research content (arguably yes, given most of it is already published academic/policy material) versus whether you'd want a routing rule at the `council-mcp` layer later that keeps anything Boox-sourced out of prompts sent to non-Western-hosted models specifically, rather than an all-or-nothing choice either way.

## Phase 2 — a real council, wrapped the same way second-brain-mcp already is

If Phase 1 proves useful enough to automate, the natural next step — given this project's own established pattern of wrapping a Python script in an MCP server (exactly what `second-brain-mcp` already does around `query.py`) — is a second small service, `council-mcp`, wrapping a `council.py` that runs the actual three-stage flow: fan out to the five models concurrently (native Anthropic SDK for Claude, OpenRouter for the rest), collect anonymized peer rankings, call `query_second_brain` internally for grounding before the chairman stage, and return one tool result containing the synthesized answer, the underlying citations, and (optionally) the individual member answers for inspection. Wiring it in as another MCP server — rather than as a raw custom OpenAI-compatible endpoint in `librechat.yaml` — keeps the integration pattern consistent with what's already proven working: a single "Research Council" agent in LibreChat gets both `council-mcp` and `second-brain-mcp` attached, with a system prompt telling it to run the full council for genuinely open or contested questions and to just query the second brain directly for straightforward lookups.

Two real costs come with this phase. It needs a new secret (`OPENROUTER_API_KEY`, which covers Gemini, DeepSeek, Kimi, and GLM in one key), which should go through the same SOPS+age `.env.enc` pattern every other pipeline already uses — no reason to break that discipline here. And it needs somewhere to run: a five-model-plus-chairman fan-out is bursty CPU/network load, not the kind of thing this NAS's tight headroom (2 cores, ~7GB, already stretched enough that MongoDB had to move to Atlas over an AVX gap) obviously wants to absorb on top of everything else it's running. Given deferred architecture decision #1 (the possible NAS-to-VPS split) is already an open question, `council-mcp` is a reasonable candidate to build directly on the VPS if that migration happens, or to hold off building until that decision resolves, rather than adding more load to the NAS in the meantime.

## Integrating Perplexity's Model Council ideas into `council-mcp`

Perplexity's design isn't just a competing product to note and move past — three of its choices are worth pulling directly into `council-mcp`'s design, and one is worth deliberately not copying.

The first is making roster size and depth a per-query dial rather than a fixed five-member, three-stage pipeline. Design `run_council` as an MCP tool that takes `question`, an optional `models` list (defaulting to the five-seat roster above), an optional `chair`, and a `depth` flag — `"quick"` runs two or three members straight to chair synthesis with no peer-ranking round, `"full"` runs the whole roster through Karpathy's complete three-stage flow including peer review. This directly answers the cost weakness raised above: instead of every council query costing roughly six model calls regardless of how much the question actually needs, a quick sanity-check on a narrow question can run two members for a fraction of the cost, and the full peer-reviewed council is reserved for the genuinely contested, high-stakes questions it's actually suited to. The "Research Council" agent's system prompt can pick a sensible default depth itself based on how open-ended the question looks, with you able to override it.

The second is treating each council member as a real tool-using subagent rather than a single-shot completion fed pre-fetched context. Perplexity's description — "the orchestrator spins up parallel subagents, each acting as a full agent that works the problem independently" — implies each model decides for itself what to retrieve, not that it's handed one shared context block before generating. `council-mcp` should do the same: give each member model's own function-calling its own access to `query_second_brain` (most current frontier and open-weight models, including all five in the roster above, support tool calling through OpenRouter), and let each one decide what to search for and when, rather than centralizing retrieval into one shared call before fan-out. This costs more MCP round-trips per query — though those are cheap, since embedding search is local — but it means five members searching your vault five different ways is itself part of the diversity signal a council is supposed to provide, rather than five models all reasoning over the identical retrieved passages.

The third is structuring the chairman's output the way Perplexity frames its synthesizer's job — explicit agreement and divergence, not just a blended paragraph. Have the chairman's system prompt (and, if you build structured tool output for `run_council`, its return schema) require three distinct sections: a consensus summary, a divergence summary naming which member(s) took which position and why, and a citations list carried through from whichever `query_second_brain` calls the members and chairman actually made. That makes the interpretive-disagreement signal — the actual value case for a council on your research questions — something you can scan directly, rather than something you have to infer from reading five paragraphs of prose.

What's deliberately not worth copying is dropping the peer-review stage outright the way Perplexity did — better to keep it available as the `"full"` depth option rather than removing it, since for your specific use case (contested governance framings, not general search) the peer-ranking signal is more valuable than it is for Perplexity's broader consumer research queries, even accounting for the self-preference-bias caveat already raised.

One further idea worth flagging as a real but separate extension, not part of the core build: Perplexity's actual strength is live web search, and their newer Agent API supports MCP connections. If `council-mcp` or the chairman is ever given a Perplexity-backed search tool alongside `query_second_brain`, that draws a genuinely useful distinction your vault-only grounding can't — "what does my own library already say" versus "what's been published since, or beyond what I've saved." That's a meaningful capability, not just redundant grounding, but it's also a new paid dependency and a second jurisdiction question layered on top of the one already raised about the Chinese council members, so it belongs as a later addition once the core vault-grounded council is built and proven, not folded into Phase 2.

## Strengths and weaknesses of running your research this way

The genuine strength of a council, for the kind of work this vault is built around, is that it's suited to interpretation and framing rather than fact retrieval. Your own wiki design notes already flag live, contested framings in your source material — multistakeholder versus multilateral governance, how digital sovereignty gets defined, where AI-governance-for-the-Global-Majority arguments diverge from mainstream framings — and these are exactly the kind of question where several models grounded in the same retrieved passages from your library can surface disagreement explicitly instead of handing you one confident-sounding take that happens to reflect one model's particular leanings. Because every council member and the chairman would be grounded through the same `query_second_brain` call, disagreement in a council answer is more likely to reflect a real interpretive split in the sources than the models simply hallucinating differently, which is a meaningfully different and more useful signal for a research workflow than an ungrounded council would give you. Mixing in genuinely different-lineage models — the Chinese open-weight models scoped above, not just more Western frontier models — is what makes this strength real rather than cosmetic.

The weaknesses are worth taking as seriously as the strengths, and mostly cut against always reaching for the council by default. Cost and latency multiply directly — five frontier-model calls plus a chairman call is roughly six times a single query's cost and wall-clock time, and every one of those models is a paid API with no local option in practice, which sits oddly against a project that has otherwise gone out of its way to keep processing local and free wherever it can (embeddings run entirely on-CPU specifically so that `--synthesize` remains, in your own words, "the only place this pipeline spends money on an LLM"). A council habit risks quietly becoming the most expensive part of the whole stack if it's used for questions a single grounded query would have answered just as well — and your own karpathy-llm-wiki-implications.md doc already flagged this exact tension for the wiki-synthesis-versus-retrieval question; the same caution applies one layer up, to council-synthesis-versus-retrieval.

Models agreeing is also weaker evidence than it looks, even across a more diverse roster. Frontier models still share a fair amount of overlapping pretraining data and broadly similar RLHF-style alignment, especially on contested policy topics, so convergence across the council can mean "this is the internet's median take" rather than "this is correct" — genuine diversity of training data and institutional origin matters more than headcount, which is the whole rationale for trading some Western seats for Chinese open-weight ones above rather than just adding more members. The peer-ranking step compounds this risk rather than resolving it: it's itself LLM judgment, and LLM judges have a documented tendency toward self-preference and verbosity bias even when identities are anonymized, so a chairman's account of "which answer the council rated highest" should be read as one more input to your own judgment, not as a verdict. And because the chairman's job is to blend several answers into one, there's a real risk of citation-grade provenance — the thing this whole vault design has prioritized from the start — getting smoothed away in the synthesis; worth explicitly requiring the chairman prompt to carry every underlying citation through rather than paraphrasing them into unsourced prose, the same "structured scaffolding, not finished prose" discipline you already applied to the wiki layer.

Net recommendation: build Phase 1 now, since it costs nothing beyond config and will tell you within a few real research questions whether the council genuinely earns its cost on your topics; treat Phase 2's automation as worth building once that's answered, and time it against the VPS decision rather than adding more concurrent load to the NAS in the meantime.
